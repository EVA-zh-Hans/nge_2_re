# f2info.bin / TEXT 文件结构与运行时白皮书

## 1. 结论摘要

`free/f2info.bin` 是一个通用 `TEXT` 容器，机密信息菜单通过 32 位键查找记录，
再把记录中的字符串交给专用详情渲染器。

本次结合原版 `ULJS00064` 文件、仓库解析器和 EBOOT 反编译确认：

- `TEXT` 容器由 16 字节头、8 字节索引项和变长字符串记录组成。
- `f2info.bin` 的查找键为 `topic_id | (access_level << 8)`。
- 字符串记录前 8 字节是两个元数据字段，游戏显示时使用 `record + 8`。
- 详情文本前两行分别是页数和标题。
- `$n` 是详情渲染器唯一识别的翻页控制符。
- 每页正文只有 6 个固定渲染槽，其中 1 个用于标题后的空白行，因此正文最多 5 行。
- 换行处理没有正文槽边界检查。单页正文超限会覆盖相邻栈数据，可导致卡死或崩溃。

因此，`f2info.bin` 翻译不能按普通自由文本处理。导出器必须验证人工排版，
发现违规时拒绝导出，不能静默换行、分页或回退原文。

## 2. 分层视图

从上到下可分为四层：

1. 文件容器层：`TEXT` 头、索引和字符串记录。
2. 业务索引层：机密信息主题与访问等级组成的 32 位键。
3. 详情文本层：页数、标题、正文行和 `$n`。
4. UI 渲染层：固定数量文本对象、翻页动画和按键等待。

卡死问题发生在第 4 层，但由第 3 层的非法排版触发。

## 3. TEXT 容器格式

所有整数均为 32 位小端。

### 3.1 文件头

| 偏移 | 大小 | 类型 | 含义 |
|---:|---:|---|---|
| `0x00` | 4 | `char[4]` | 固定魔数 `TEXT` |
| `0x04` | 4 | `uint32` | 索引项数量 |
| `0x08` | 4 | `uint32` | 索引表偏移，标准文件为 `0x10` |
| `0x0C` | 4 | `uint32` | 字符串区起始偏移 |

原版 `f2info.bin`：

```text
magic              = "TEXT"
entry_count        = 97
entry_table_offset = 0x10
content_offset     = 0x318
file_size          = 22788
```

### 3.2 索引项

索引表从 `entry_table_offset` 开始，每项 8 字节：

```c
struct TextFileEntry {
    uint32_t key;
    uint32_t string_offset;
};
```

`string_offset` 是相对于文件起始位置的绝对偏移。

游戏函数 `TextArchive_FindByKey` 从头线性扫描索引。若相邻索引项具有相同键，
游戏会随机选择其中一项。原版 `f2info.bin` 的 97 个键均唯一。

### 3.3 字符串记录

```c
struct TextStringRecord {
    uint32_t unknown0;
    uint32_t unknown1;
    char text[];
};
```

- `text` 使用游戏 Shift-JIS/自定义中文字库编码。
- 文本以 NUL 结束，记录按 4 字节对齐。
- `f2info.bin` 中两个元数据字段当前均为 0。
- 机密信息菜单把查找结果加 `8` 后传给详情渲染器。

索引项可共享同一字符串记录。物理记录顺序不要求与索引顺序一致。例如原版
第一个键 `0x00000000` 指向文件后部的“无数据”字符串。

## 4. f2info 业务键

菜单打开详情时使用：

```c
key = topic_id | (access_level << 8);
```

| 位 | 含义 |
|---|---|
| `0..7` | `topic_id`，当前为 `1..24` |
| `8..15` | `access_level`，当前为 `0..3` |
| `16..31` | 当前未使用 |

示例：

| 键 | 主题 | 等级 |
|---:|---:|---:|
| `0x00000001` | 1 | 0 |
| `0x00000101` | 1 | 1 |
| `0x00000201` | 1 | 2 |
| `0x00000301` | 1 | 3 |

键 `0` 是“无对应数据”占位记录。

## 5. 详情文本语法

原版记录采用以下形式：

```text
２
EVA的构造：一般情报

　第一页第一行
　第一页第二行
　第一页第三行$n

　第二页第一行
　第二页第二行
```

对应的精确字符结构：

```text
<全角页数>\n
<标题>\n
\n
<第一页正文，最多 5 行>$n
\n
\n
<第二页正文，最多 5 行>\n
```

规则：

- 第一行必须是一个全角数字 `１` 至 `９`。
- 第一行数值必须等于 `$n` 数量加 1。
- 第二行是标题。
- 标题后必须保留一个空行。
- 第一页正文前是一个 LF。
- 后续每页在 `$n` 后使用两个 LF。
- 非末页的最后一个正文字符后应立即放置 `$n`。
- 末页以 LF 结束。
- `$n` 只能表示翻页，不能当普通文本使用。

## 6. 游戏渲染逻辑

相关 IDA 地址和本次写回名称：

| 地址 | 名称 | 作用 |
|---:|---|---|
| `0x08810A78` | `TextArchive_Load` | 加载完整 TEXT 文件 |
| `0x08810414` | `TextArchive_FindByKey` | 查键并返回字符串记录 |
| `0x08810B44` | `TextArchive_Close` | 释放 TEXT 文件 |
| `0x088D6B10` | `InfoMenu_Run` | 机密信息菜单主循环 |
| `0x088D7C78` | `InfoMenu_OpenDetail` | 合成键、加载记录并打开详情 |
| `0x088D7790` | `InfoDetail_ShowText` | 解析详情文本并处理翻页 |

`InfoDetail_ShowText` 的主要流程：

1. 扫描至第一个 LF，取得页数文本。
2. 扫描至第二个 LF，取得标题。
3. 从正文开始逐字节读取。
4. 遇到 LF，把当前内容提交到下一个正文文本对象。
5. 遇到 `$n`，显示当前页并等待确认/取消键。
6. 清理当前页，再从下一页第一个正文槽继续。

详情界面虽然创建了 7 个行文本对象，但正文淡入、淡出和清理循环只处理固定的
6 个正文对象，对应索引 `2..7`。标题后的空白行占一个槽，所以每页最多放置
5 行实际正文。

## 7. 卡死根因

`InfoDetail_ShowText` 在 `0x088D7C44` 处理 LF：

```text
提交当前行
正文槽索引 += 1
```

这里没有检查索引是否仍在 `2..7`。后续提交会把栈上的相邻数据解释为文本对象
句柄并调用渲染函数，结果可能是：

- 写坏局部变量或保存寄存器；
- 访问无效文本对象；
- 在等待按键或动画循环中进入不可恢复状态；
- 直接崩溃。

当前下载翻译中已经存在确定触发条件。例如 `info.json` 第 67 条
（键 `0985ddb95a277d4d7b47256154ab064b`）首行声明 3 页，但没有 `$n`，
全部正文落在同一页，并形成 7 行以上正文。

“有时候打开或翻页卡死”与该行为吻合：只有进入违规条目或翻到违规页时才触发。

## 8. 翻译边界

### 8.1 硬性安全边界

违反以下规则必须拒绝导出：

- 必须存在页数行、标题行和标题后的空行。
- 页数必须是一个全角数字 `１..９`。
- 页数必须等于实际页数。
- 每页最多 5 行正文，包括人工保留的正文空行。
- 翻页必须使用精确的 `$n\n\n` 结构。
- 禁止嵌入 NUL。
- 禁止 CR/CRLF，统一使用 LF。
- 禁止 `%`。底层文本函数把内容当作格式字符串，`%` 可能读取不存在的参数。

### 8.2 保守版面边界

以下上限来自原版全部 97 条记录的最大值：

| 区域 | 编码后最大字节数 |
|---|---:|
| 标题 | 34 |
| 单行正文 | 54 |

计数必须使用 `common.to_eva_sjis()` 的实际结果，不能按 Unicode 字符数估算。
中文通常占 2 字节，ASCII 通常占 1 字节。

这些上限主要保证与原版版面、屏幕宽度和现有字库渲染行为一致。即使较长行不一定
立即破坏栈，也不应依赖越界显示或底层文本对象的隐式裁剪。

### 8.3 翻译工作建议

- 以原文的页数、分页位置和行数为模板。
- 优先改写句子，而不是删除换行后依赖自动换行。
- 需要增加页数时，人工插入 `$n`，同步修改第一行页数。
- 不要在导入脚本中自动折行或自动分页。
- 每次修改后运行导出；校验失败时按报错中的条目、页和行修正。
- 不要只检查视觉长度，必须检查游戏编码后的字节长度。

## 9. 仓库实现评估

`app/parser/tools/text.py` 对当前标准 `TEXT` 文件的核心理解是正确的：

- 正确读取魔数、数量、表偏移和内容偏移。
- 正确读取 `{key, string_offset}` 索引。
- 正确读取字符串记录的两个 32 位元数据字段。
- 正确按偏移去重，并保持索引到字符串的引用关系。
- 正确按 4 字节块读取 NUL 结尾文本。

需要明确的限制：

- 保存器生成的是规范化布局，不保证与输入文件逐字节一致。
- 保存器固定写 16 字节头和连续索引表，不保留非标准 padding。
- 未被任何索引引用的字符串记录不会保留。
- 相同字符串可能被数据库重建逻辑重新去重，物理偏移会变化。
- 这些变化不影响当前 `f2info.bin` 的游戏查找语义，但不应直接推广为任意
  `TEXT` 变体的无损编辑保证。

数据库重建现已按 `entry_index` 排序，而不是依赖数据库自增 `id`。

## 10. 导出校验策略

`app/parser/tools/info_text.py` 只做验证，不修改文本：

- 不自动折行；
- 不自动插入 `$n`；
- 不自动修改页数；
- 不静默回退原文。

`TextEntryDao.rebuild_text_archive()` 会收集所有 `f2info.bin` 翻译错误，并在保存
前抛出异常，拒绝生成危险文件。

建议验证路径：

```bash
uv run -m pytest tests/unit/test_info_text.py
make export_all
```

导出通过后，仍应在 PPSSPP 或真机逐项打开机密信息并翻完所有页面。

## 11. 反编译证据边界

本白皮书中“固定 6 个正文槽”“换行索引无边界检查”“键合成方式”来自 EBOOT
反编译和汇编，可视为已确认行为。

标题 34 字节、正文 54 字节是原版数据集的经验上限，是保守兼容约束，不是已经
证明的底层内存分配极限。若未来要放宽，应先在 PPSSPP 和真机验证字体宽度、
裁剪行为和格式化文本缓冲区，再修改校验器。
